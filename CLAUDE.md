# FuturaTecno — Cheat Sheet

## Stack
- **Backend:** Java 21 + Spring Boot 3.3 + Spring Security + JWT + JPA/Hibernate + Flyway + PostgreSQL 16
- **Frontend:** React 18 + Vite + React Router + axios + Context auth | **JSX (no TypeScript)**
- **AI:** tres usos — generar listados de catálogo desde texto/Notion, clasificar categorías (último recurso, después de `ClasificadorPorNombre`) y buscar imágenes. El proveedor se elige con `CATALOGO_IA_PROVIDER` (`anthropic` | `openai` | `deepseek`), **uno solo y sin fallback automático**: un fallback duplicaría el gasto en silencio. **Producción corre con `anthropic`** desde 2026-09-14: DeepSeek encola indefinidamente las requests que salen de Railway (ver bullet propio) y el tope de gasto de Anthropic resultó ser **un límite puesto por nosotros**, no de Anthropic — se subió en Settings → Billing y quedó liberado (probado: 200 en 1,17 s). Todo degrada solo si no hay clave: la clasificación deja `categoria_id` en null para corregir a mano en Admin → Productos. Para imágenes, ver el bullet propio más abajo: no todos los proveedores sirven.
- **Exchange rate:** dolarapi.com dólar oficial (cacheado en memoria)
- **Deploy:** Railway, push a `main` = auto-deploy (~90 s – 3 min) | URL: `https://www.futuratecno.com.ar` (la de Railway, `https://futuratecno-production.up.railway.app`, sigue viva)

## Arquitectura no obvia
- **Frontend embebido en el jar:** Vite buildea a `backend/src/main/resources/static/` → mismo origen que el backend → sin CORS. El `Dockerfile` hace el build del frontend primero.
- **Sin Lombok:** se rompió bajo Java 25 durante el desarrollo → getters/setters explícitos en todas las entidades. No agregar Lombok.
- **Flyway activo (`ddl-auto=validate`):** las migraciones van en `backend/src/main/resources/db/migration/` (ya hay **V1–V45**; la próxima libre es **V46**). Cualquier cambio de schema necesita un archivo nuevo. **No cambiar a `ddl-auto=update`.**
- **Fórmula de precios:** `(costo USD) × (1 + flete%) × (1 + margen%)`, y vive **solo** en `PrecioService` — la usan el catálogo, los pedidos y el envío; si se duplicara, un cliente podría ver un precio y que se le registre otro. El flete es **porcentaje**, no monto fijo. Defaults del proveedor: flete 5%, margen 15%.
- **Margen y flete se pueden pisar por producto (V41).** `productos.margen_porcentaje` / `flete_porcentaje`, opcionales: **null = usar el del proveedor**, que NO es lo mismo que 0% (eso sería vender al costo) — por eso se compara contra null y no se hace coalesce a cero. Se editan en Admin → Productos, con el valor del proveedor como placeholder. El override se recuerda en `margenes_manuales`, y esa memoria **lleva el proveedor en la clave**, a diferencia de las otras (imágenes, descripciones, atributos): la foto de un iPhone 15 es la misma venga de donde venga, pero el margen está atado a lo que ESE mayorista te cobra, y cruzarlo daría un precio equivocado en silencio. Vaciar los dos campos borra la memoria. Cambiar el margen mueve el precio público al instante, pero **no toca pedidos ya confirmados**: esos guardan importes congelados.
- **Soft delete:** `activo=false` en `Producto` y `Variante`. Nunca borrar físicamente.
- **Imagen por PRODUCTO** (no por variante): `Producto.imagenUrl`. Una sola imagen por producto independientemente de cuántas variantes tenga.
- **MercadoLibre bloquea scraping server-side** → cualquier request no-browser devuelve 302 a "suspicious-traffic". Las imágenes ML no se pueden auto-obtener. Flujo manual: Admin → Imágenes → "🔍 Buscar" abre Google Images → el usuario copia la URL de la imagen → la pega → preview → Guardar.
- **Búsqueda de imágenes: hay DOS caminos distintos y no hacen lo mismo.** Admin → Imágenes (`ProductoAdminService#buscarImagenesFaltantes`) recorre una cascada de cuatro fuentes: **Icecat → Google CSE → DuckDuckGo → Anthropic**. El panel Cargar JSON (`GenerarListadoService#imagen`) consulta **una sola**: Anthropic, u OpenAI si `CATALOGO_IA_PROVIDER=openai`. **DeepSeek no tiene búsqueda web alojada**, así que apuntar ahí deja al generador cayendo igual en Anthropic. Estado al 2026-09-14: **debería volver a encontrar imágenes**, porque el 400 de Anthropic que mataba las dos vías era el tope de gasto propio y ya se subió (falta confirmarlo con una búsqueda real). Igual quedan dos fuentes apagadas: Icecat y Google no tienen variables en Railway. Unificar el generador con la cascada de cuatro sigue valiendo la pena: hoy una sola cuota agotada apaga las imágenes enteras.
- **Prompt del generador (Cargar por JSON → Texto del proveedor), 2026-09-26.** `GenerarListadoService.INSTRUCCIONES` = el prompt del usuario ("Json artículos electrónica") + las reglas acordadas: TODOS los precios son USD (también con "$"), RAM/disco/placa/color/tamaño dentro del modelo, un artículo por color, categorías con las rutas reales, `imagenes: []`, excluir usados/open box y avisos. El normalizador acepta también un array directo y deja pasar `modelo_exacto` y `especificaciones.color`. La imagen del borrador busca exacta → **mismo modelo** (`buscarPorFamilia`) → internet. Es el mismo contenido que `outputs/prompt-json-articulos.md` (para usar con otra IA): si se cambia uno, cambiar el otro. **Las listas largas se parten en tandas en paralelo** (`tandas`: ~1.800 caracteres o 25 líneas con precio, cortando solo ANTES de una línea con precio para no separar un artículo de sus colores, y arrastrando el último encabezado): una sola llamada tiene tope de respuesta (~100-120 artículos contando cada color) y la lista de Cozzo de 6.847 caracteres lo pasaba ("La generación no terminó completa"). `unir` junta las partes con el mismo criterio de duplicados; si una parte falla, falla todo con "Parte N de M: …".
- **Un producto cargado por JSON tiene UNA sola variante (V35).** La capacidad, el color y la versión SIM/eSIM viajan **dentro del modelo** (`iPhone 17 Pro 256GB eSIM`), porque así se lo pedimos a la IA en el prompt de `GenerarListadoService`. O sea que `Variante.especificaciones` en esta vía es una **descripción**, no algo que distinga: nunca usarla como clave de búsqueda. Se hizo, y el resultado fue que cada vez que la IA redactaba distinto (`256GB · Versión eSIM` vs `256GB · eSIM`) nacía una variante nueva en lugar de actualizarse el precio — 23 productos con el mismo teléfono ofrecido dos veces a precios distintos. Como el precio del pedido **se congela al confirmar**, el cliente elegía la barata (la vieja) y se vendía por debajo del costo del día: hasta US$ 111 en un iPhone 17 Pro 512GB. Elit e Invid importan por otro camino y ahí las variantes múltiples **sí** son reales.
- **La imagen se busca en TRES lugares antes de gastar un crédito (V36).** `ImagenManualService#buscar` mira, en orden: `imagenes_manuales` → `imagenes_automaticas` → **el catálogo en vivo** (`productos.imagen_url`, prefiriendo el activo). La tercera es la que más ahorra y la que faltaba: las tablas de memoria solo se escriben al editar a mano, al encontrar buscando o al dar de baja, **nunca** cuando el artículo entra con foto desde un mayorista o una carga JSON — o sea que el 98% del catálogo (3.215 productos al 2026-09-14) tenía imagen y el generador salía a pagar por ella igual. La consulta compara marca y modelo normalizados, así que necesita el **índice funcional de la V36**; si alguna vez cambia la normalización en Java hay que cambiar el índice, o deja de usarse en silencio. Además, una imagen nueva que llega en un borrador se recuerda al importar, para que el próximo listado no vuelva a pagarla.
- **La URL del JSON se verifica antes de publicarla.** `imagenesLimpias` solo chequeaba que empezara por `http`, así que una URL muerta se publicaba como foto rota **y se guardaba en `imagenes_automaticas`**: a partir de ahí toda carga futura de ese marca+modelo la encontraba en la memoria y la reusaba, convirtiendo el error de un día en permanente. Ahora `CargaJsonService#soloVivas` la pasa por `ImageUrlValidatorService` (pide 1.024 bytes con `Range`, exige 2xx + `content-type: image/*` + firma de bytes real, sigue hasta 3 redirects, 3 s/5 s). Si no valida, el producto queda **sin imagen** y el resultado de la carga lo avisa por artículo. **Solo corre cuando la imagen va a usarse** — o sea, cuando la base no tenía nada —, así que recargar un listado ya cargado no dispara ni una petición. Caso real: las URLs de `motorolaar.vtexassets.com` devuelven un JSON 400 ("No account could be identified for the host"), no una imagen. **La foto que viene de la MEMORIA también se verifica (2026-09-25)**, pero solo cuando va a cambiar la del producto, y solo se descarta con **404/410** (`ImageUrlValidatorService#verificar` → `MUERTA`): un 403, un 5xx o un timeout quedan `DUDOSA` y se usa igual, porque puede ser un sitio que bloquea datacenters. La URL muerta se borra de las dos memorias (`ImagenManualService#olvidarUrl`) y la carga lo avisa por artículo. Vino de un caso real: seis Galaxy heredaron URLs inventadas de `images.samsung.com` que daban 404. Rige también para Admin → Imágenes → buscar faltantes.
- **Foto prestada de la misma familia (2026-09-26).** Si no hay foto recordada ni URL válida en el JSON, `ImagenManualService#buscarPorFamilia` usa la de un producto de la misma marca cuyo modelo solo cambia en lo que no se ve: capacidad, RAM, teclado, conectividad, núcleos, procesador (Core/Ryzen/Snapdragon/chips M de Apple), placa de video, panel (OLED, 144Hz, WUXGA, tamaño con decimales), disco, sistema operativo y opciones comerciales del proveedor (ABM OPT, CTO, sellado, eSIM…) (`claveFamilia`; pedido del usuario: en la base importan marca y modelo). iMac M4 24" 256GB ≈ 1TB, LOQ 15ARP10E Ryzen 7 170 ≈ 7735HS; iPhone 17 Pro ≠ 17 Pro Max y MacBook Pro 14 ≠ 16 (el tamaño entero queda). **Reglas de color acordadas con el usuario:** si el artículo dice UN color, solo sirve un pariente de ese mismo color (un iPhone plateado en la ficha del naranja es otro producto); si no dice color o lista varios, se prefiere gris/plata, después negro, después un pariente sin color. Corre en la carga JSON (después de la URL del JSON) y en Admin → Imágenes. **Ahí hay dos botones (2026-09-26):** "Buscar en la base" (`/buscar-imagenes-base`) recorre TODOS los productos sin foto de una vez, solo con memoria + familia, y verifica los 404 en paralelo; "Buscar en internet" (`/buscar-imagenes-internet`) va de a 10, mira la base primero (gratis) y marca `imagen_busqueda_at` en cada producto intentado, así el clic siguiente sigue con los 10 que nunca se buscaron (cuando se intentaron todos, vuelve a los más viejos). **No se guarda en la memoria de imágenes**: es prestada, y una propia que aparezca después tiene que poder reemplazarla. Medido al 2026-09-26: 98 de 267 productos sin foto.
- **Si el match exacto falla, hay una CLAVE SUELTA (V37).** Las tres fuentes de arriba comparan marca+modelo exactos, y el modelo lo redacta la IA distinto en cada carga: `256GB` / `256 GB` / `(eSIM)` / `e-SIM` hacían nacer un producto nuevo, sin imagen, para cargar a mano de nuevo. Como último intento antes de pagar una búsqueda, `ImagenManualService#buscarSuelto` compara `productos.clave_suelta`: **minúsculas y solo `[a-z0-9]`**, con la marca sacada del modelo si viene repetida (`Apple` + `Apple Pencil Pro` = `Apple` + `Pencil Pro`). Absorbe la redacción sin perder lo que distingue: `256gb` ≠ `512gb`, `black` ≠ `white`, `mini5pro` ≠ `mini5proplus`. **La expresión está replicada en dos lados** — la columna generada de la V37 y `ImagenManualService#clave` — y si se cambia una sin la otra las búsquedas dejan de encontrar en silencio; por eso la regla es la más tonta posible (las tildes se caen enteras en ambos). La misma clave decide también **si el producto ya existe** en la carga JSON (`CargaJsonService`): exacto primero, suelta después. Sin eso, cada redacción nueva creaba un producto aparte — el mismo artículo publicado dos veces a precios distintos y sin imagen. Cuando matchea por clave suelta **no se pisa el modelo guardado**: el nombre que ve el cliente no tiene que cambiar según cómo lo redactó la IA esta vez. Elit e Invid no pasan por acá: deduplican por `codigo_externo`, que es estable.
- **Identidad del artículo en la carga JSON (V42, 2026-09-24).** Qué producto es cada artículo ya NO lo decide el nombre sino `IdentidadProductoService`: reglas deterministas y versionadas (`telefono-v1` / `generico-v1`, la versión viaja en la clave: `tel1|motorola|g04|4g|64|4|…`) que extraen de marca + modelo + especificaciones el modelo base, conectividad, almacenamiento, RAM física, SIM/eSIM, color, condición, combo y región. "G04 4G 64GB / 4GB RAM" y "Motorola G04 4G 64GB" con `ram: "4GB"` convergen; 64/128GB, 4/8GB de RAM y G04/G04s no. Lo que no es teléfono usa la clave suelta de siempre. Reglas que costó aprender:
  - **Un dato desconocido no es comodín.** Falta RAM (Android) o almacenamiento, o el nombre contradice a las especificaciones → `revision`: no crea ni actualiza. Un producto existente al que le falta un dato que el entrante tiene (o al revés) es `CONFLICTO` → revisión. El iPhone no exige RAM.
  - **4G ≠ 4GB, y la RAM virtual no es RAM** ("8GB+8GB" = 8). En especificaciones, la conectividad es la generación más alta (las fichas listan "5G, 4G LTE") y el color solo cuenta si hay uno (varios = colores disponibles). Medido: sin esas dos reglas, 1 de cada 10 fichas reales iba a revisión.
  - **El nombre exacto y la clave suelta solo traen candidatos; decide la comparación de atributos** (`CargaJsonService#decidir`). Duplicados históricos: si exactamente uno está activo se actualiza ese (así se consolidaron el 18/9); si no, revisión.
  - **Unicidad en la base:** índice único parcial `(proveedor_id, identidad_clave) WHERE identidad_clave IS NOT NULL`, incluye inactivos (recargar reactiva el mismo id). La carga toma `pg_advisory_xact_lock` por proveedor+familia **en orden** antes de consultar: probado que sin el lock dos cargas simultáneas chocan contra el índice. Elit/Invid siguen por `codigo_externo`.
  - **Memorias:** imagen, descripción, atributos y margen se buscan por todos los nombres del artículo (el guardado, el entrante y los de otros productos con la misma identidad, ver `NombreArticulo`). Antes se buscaban con el modelo entrante y una redacción nueva pisaba la descripción manual.
  - **Transición:** los productos anteriores a la V42 no tienen identidad (la carga los resuelve al vuelo y adopta al inequívoco). `GET /api/admin/identidad/transicion` informa inequívocos, duplicados (con líneas de pedido que los referencian) y ambiguos; `POST …/asignar` asigna SOLO a los inequívocos. Nada se fusiona ni se da de baja solo.
  - `Variante.ramGb/almacenamientoGb/color` se llenan como **proyección** de la identidad; la fuente de verdad es `productos.identidad_*`.
  - **RAM y disco al nombre (2026-09-26).** Lo que no es teléfono se identifica por el NOMBRE, y la IA deja la RAM y el disco de las notebooks solo en la ficha: "HP 250 G10 i7-1355U" de 8/256 y de 16/1TB eran la misma identidad y del segundo en adelante iban a revisión ("el mismo artículo ya aparece en la fila N": 70 notebooks en un día). Ahora `CargaJsonService#capacidadesFaltantes` agrega al modelo la RAM/almacenamiento de la ficha que el nombre no dice ("16/512" y "16GB" cuentan como dichos; "MacBook Pro 16" no es RAM) **antes** de resolver la identidad. **También la placa de video dedicada** (`gpuFaltante`: "RTX 5070 Ti", "RX 7600S"; las integradas no): la MSI Raider 16 Max 32GB/1TB viene con 5070 Ti, 5080 y 5090 a precios distintos. Transición: si con el nombre largo no hay candidato, se busca UN producto activo del proveedor con alguno de los nombres anteriores (el corto, con RAM y disco pero sin placa, o —si la IA ya escribió la placa en el nombre— lo que viene antes de la placa, `antesDeLaPlaca`) y la misma RAM, disco y placa en la ficha (`conNombreCorto`), se actualiza y se le completa el nombre; si la ficha no coincide, es otra variante y se crea aparte.
  - **Colores en inglés, con el nombre del fabricante (2026-09-26, pedido del usuario).** Nunca se traducen: "Citrus" no es "Naranja". El prompt del generador lo pide, `nombreAlCrear` agrega el color de la ficha tal como vino (o el reconocido pasado al inglés, `nombreColorIngles`) y la etiqueta de color del admin (`coloresVisibles`) sale en inglés. Transición: un artículo que solo cambia en el idioma del color respecto de uno publicado del mismo proveedor (`soloCambiaElIdiomaDelColor`) se adopta —lo que no es teléfono se identifica por el nombre y si no duplicaba "… Plateado" con "… Silver"— y el nombre pasa al inglés; solo en esa dirección, así una lista vieja en castellano no lo retraduce. La identidad no cambia: "negro" y "black" siguen siendo el mismo color canónico.
  - **Marca repetida y `modelo_exacto`:** la marca al inicio del modelo se saca al importar (cualquier fuente, no solo el generador: la skill `json-articulos-electronica` la repetía) → no más "Motorola Motorola G04". Si `modelo_exacto` dice algo que `modelo` no (típico: el color), se usa para la identidad, y al CREAR el producto el color se agrega al nombre ("G04 4G 64GB Verde").
- **Memoria por marca+modelo (V31–V34):** cuatro tablas con la misma clave (`marca`, `modelo` normalizados a minúsculas y espacios colapsados) para que el trabajo manual sobreviva a un reimport y se comparta entre proveedores: `imagenes_manuales` (V31), `imagenes_automaticas` (V32), `descripciones_manuales` (V33) y `atributos_manuales` (V34: categoría + peso/dimensiones). Dos detalles que no se deducen del código:
  - **La "descripción" es `Variante.especificaciones`** — no existe columna `descripcion` en `Producto`.
  - **V33 EXCLUYE Elit/Invid** a propósito (reescriben su ficha en cada sync, recordarla taparía la descripción propia); **V34 los INCLUYE**, porque ningún mayorista trae peso ni dimensiones y una medida real es cierta venga de donde venga. V34 además **solo rellena huecos**, nunca pisa un dato cargado.
- **Depurar catálogo (Admin → Depurar catálogo).** Saca de la tienda lo que no da señales de vigencia hace N días (default 3). **La señal NO es `updated_at`** — ese responde "¿cambió algo?", no "¿el mayorista lo sigue teniendo?". Medido el 2026-09-16: una importación de Invid informó 1.188 actualizados y **solo 70** movieron la fecha, porque el resto vino con precio y stock idénticos y Hibernate no emitió UPDATE. Filtrar por ahí habría propuesto dar de baja 1.134 productos vigentes. Por eso la V40 agregó `productos.visto_en_sync_at`, que los imports de Elit/Invid escriben para **cada producto que encuentran en el feed**, cambie o no. `ProductoAdminService#senalDeVigencia` usa esa columna. **La carga por JSON también la escribe (2026-10-01)** para cada artículo que viene en el listado (creado o actualizado): antes caía a `ultimaActualizacion` creyendo que ahí era honesta, pero un artículo que llegaba con el mismo precio tampoco movía la fecha — medido: 554 de 1.179 de Kadabra parecían discontinuados el mismo día que se cargó su lista. Lo que todavía no pasó por una carga nueva sigue cayendo a `ultimaActualizacion`. Se escribe con un **UPDATE masivo por ids** (`marcarVistos`) a propósito: un `save()` por producto dispararía `@PreUpdate` y el catálogo pasaría a decir "Actualizado: hoy" en todo. Sigue en pie el otro riesgo: si la sync se **corta**, la señal tampoco se mueve — la pantalla avisa cuando hay Elit/Invid en la lista y conviene mirar los logs antes de dar de baja en masa. `GET /vencidos` es solo lectura y la baja va por `dar-de-baja` **con los ids que confirmó el admin**, nunca con el criterio.
- **Invid no manda cantidad de stock.** La API trae `STOCK_STATUS` ("Disponible", "Stock bajo", "Menos de 10 unidades"), no `STOCK`: leer solo `STOCK` dejó todo Invid con stock 0 hasta el 2026-10-04. `InvidImportService#stock` lo traduce a un número aproximado (10/5/2, 0 si "sin stock"/"agotado"); el stock solo lo ve el admin.
- **La sync de Invid reintenta sola ante el rate limit.** Invid corta a las 50 consultas/hora y su catálogo entero no entra en una tanda (pasó el 2026-09-16 a las 09:30). Antes el scheduler logueaba el error y no volvía hasta el día siguiente: dos días así y sus ~1.200 productos cruzaban el umbral de Depurar catálogo como si el mayorista los hubiera discontinuado. Ahora `InvidApiClient` lanza `InvidRateLimitException` **con la espera adentro** (del header `Retry-After`, en segundos) en vez de solo un texto, y `SincronizacionScheduler` **reprograma** con `TaskScheduler` respetando esos minutos: hasta 3 intentos, 30 min si Invid no dice nada, tope de 2 h y 1 min de margen para no pegar en el borde de la ventana. **Se reprograma, no se duerme el hilo** — mismo criterio que los mails y la generación de listados. Un error que no sea de rate limit no se reintenta: no se sabe cuánto esperar. **Y cada reintento retoma donde cortó el anterior (2026-09-23):** el catálogo entero de Invid pasa las 50 páginas de 100, así que un reintento que arrancara de la página 1 volvía a cortar en la página 50 para siempre — del 21 al 23/9 no se sincronizó nada y los ~1.200 productos quedaron en el umbral de Depurar catálogo. `InvidApiClient` guarda lo bajado y la página que falló (válido 8 h) y el scheduler hace hasta **6 intentos** (6 × 50 = las 300 páginas de `TOPE_PAGINAS`).
- **Dar de baja NO pierde el trabajo manual.** Toda baja (individual, masiva o por depuración) pasa antes por `recordarParaFuturasAltas`: imagen → `imagenes_automaticas` (así no pisa una elegida a mano), categoría y medidas → `atributos_manuales`, descripción → `descripciones_manuales` salvo Elit/Invid. Como la memoria es por marca+modelo, un alta futura recupera todo aunque venga de otro proveedor y cree una fila nueva.
- **Sincronización automática diaria:** `SincronizacionScheduler` a las 06:30 AR (configurable con `SYNC_CRON`). Modo "solo existentes": actualiza precio/stock de productos ya importados, no crea nuevos.
- **Mayoristas modulares:** cada distribuidor tiene su propio `ApiClient` + `ImportService` + `Controller`. Elit y Invid conviven sin pisarse. Dedup por `codigo_externo` + `fuente`.
- **Railway bloquea la salida SMTP** (puertos 25/465/587, política antispam) → los mails **no** pueden ir por SMTP. Un intento contra `smtp.gmail.com` no falla con error de credenciales: cuelga y muere en `ConnectException: Connection timed out`, porque nunca llega a autenticar. Por eso `EmailService` manda por la **API HTTP de Resend** (443). Cualquier integración saliente nueva: verificar que no dependa de un puerto no-HTTP.
- **Los mails van asíncronos y con timeout.** `EmailService#enviarHtmlAsync` (`@EnableAsync`) — el mail es un efecto secundario y no debe demorar ni tumbar la operación que lo dispara. Sin timeout explícito, un SMTP/HTTP colgado se queda con un hilo de Tomcat indefinidamente (pasó: un `forgot-password` tardaba ~5 min).
- **Demora de entrega por proveedor (V43, 2026-09-29).** `proveedores.demora_entrega_min_dias` / `_max_dias`, los dos null = la entrega normal (3 días hábiles de `EtaService`). Se editan en Admin → Proveedores. El catálogo manda solo los días (`ProductoCatalogoDTO.demoraEntrega*`), nunca el proveedor, y el front muestra "Entrega en 15 a 20 días" en la tarjeta, el detalle (en lugar de la fecha estimada), el carrito y el checkout. Apple Trade (`APT`) quedó en 15 a 20 días por la migración. Ojo: el SKU camuflado (`APT-P7`) lleva el código corto del proveedor a propósito.
- **Órdenes manuales (V45, 2026-09-30).** Admin → Pedidos → "Nueva orden manual" (`POST /api/admin/pedidos`, `origen='MANUAL'`): para el cliente que compra por WhatsApp o en el local. Puede no tener cuenta (`usuario_id` null + `email_contacto`; si el email coincide con una cuenta activa, queda en esa cuenta y suma puntos), el precio de cada renglón se puede cambiar (el del catálogo queda en `pedido_items.precio_catalogo_usd`), no exige compra mínima y **no vence** (`vence_en` null). Un CHECK de la base exige usuario en las órdenes WEB. No manda mails: el admin comparte el comprobante (`/admin/pedidos/:numero/comprobante`, imprimible, "no válido como factura"). El cobro de una orden manual se marca a mano aunque sea Mercado Pago. El total a cobrar (efectivo −7%, recargo MP) lo calcula el mismo `totalCobroArs` que la web.
- **Pedidos: los precios se guardan CONGELADOS.** El precio de venta es derivado y se recalcula todos los días (cotización + costos del mayorista), así que `pedido_items` copia nombre, SKU, especificaciones e importes al confirmar. `producto_id`/`variante_id` quedan solo para trazabilidad — **nunca** mostrar un pedido leyendo el producto vivo, mostraría precios de hoy y no los que el cliente aceptó.
- **El backend recalcula el precio del pedido.** El carrito manda solo `varianteId` + `cantidad`. Si se confiara en un importe del cliente, cualquiera pediría un iPhone a un dólar.
- **Los pedidos vencen a las 06:30 AR** (`PedidoScheduler`), que es cuando la sync pisa precios y stock. Es un scheduler **aparte** del de sincronización a propósito: apagar `SYNC_ENABLED` no debe dejar pedidos vivos con precios viejos.
- **No se descuenta stock al pedir.** `Variante.stock` lo pisa la sync diaria, así que cualquier descuento local se perdería a la mañana. El pedido es una solicitud, no una reserva.
- **El carrito no requiere cuenta** (vive en localStorage); la sesión se pide recién al confirmar. Al abrir `/carrito` se revalidan los precios contra la API.
- **Ojo con `SecurityConfig`:** la cadena termina en `anyRequest().permitAll()`. Toda ruta privada nueva hay que listarla explícitamente (como `/api/pedidos/**`), o nace pública.
- **Los enlaces de mail (activación y reseteo) salen de `APP_PUBLIC_URL`, nunca del request.** Con `forward-headers-strategy=framework` el host del request lo puede elegir el cliente (`X-Forwarded-Host` / `Forwarded`), y un enlace de reseteo apuntando a otro dominio le entrega el token a un tercero — incluido el del admin. En dev local, para que el enlace apunte a tu máquina, definir `APP_PUBLIC_URL=http://localhost:5173` en `backend/.env`.
- **Login con Google: reglas de vinculación (`AuthService#loginConGoogle`).** La cuenta **ADMIN nunca entra por Google** (ni vinculada ni por vincular): un vínculo no se corta al cambiar la contraseña, así que quien lograra vincularse conservaría el admin. Nunca se pisa un `google_sub` ya vinculado. Y si la cuenta existente **no tenía el email verificado**, al vincular se **borra su contraseña**: el registro no exige verificar, así que esa contraseña la pudo elegir cualquiera que se registró con un email ajeno (pre-hijacking).
- **Confirmar un pedido exige `aceptaCompromiso: true` en el body.** Se valida en `PedidoService.crear()`, no solo en el checkbox del frontend — mismo criterio que el precio: no confiar en lo que manda el cliente.
- **Peso/dimensiones para envío (V14):** `Producto` tiene `pesoGramos`/`altoCm`/`anchoCm`/`largoCm` opcionales (override real, se edita en Admin → Productos). Si están en `null`, hay que resolver por el default de `Categoria` (mismos 4 campos con sufijo `_default`): primero la subcategoría (hoja), si no tiene, la categoría padre. Elit e Icecat (plan actual) no traen este dato; **Invid sí** (`WEIGHT`/`HEIGHT`/`WIDTH`/`LENGTH`, en kg/cm): desde el 2026-10-04 la importación y la sync los copian a los 4 campos del producto **solo si los 4 están vacíos** (`InvidImportService#completarMedidas`, redondeo hacia arriba, descarta 0 y valores absurdos), así nunca pisan lo cargado a mano — confirmado pegándole a la API de Icecat en vivo, el plan da `GeneralInfo`/`Gallery` pero no `FeaturesGroups` (ahí vive el peso). Los defaults por categoría se cargaron a mano en la V14 y solo se editan por SQL directo, no hay UI para eso todavía.
- **Envío por Andreani (V15):** la cotización sale de la **API Pyme** (`woocommerce-api-acom.andreani.com`), que es el middleware del plugin de WooCommerce — **no** la API corporativa (`apis.andreani.com`, esa exige contrato comercial y nunca la conseguimos). Es la única vía para una cuenta Pyme, pero Andreani podría cambiarla sin avisar: por eso `AndreaniClient` degrada con gracia y el checkout funciona igual sin cotización. Auth: la credencial del portal (Integraciones → WooCommerce) va tal cual en `Authorization` a `POST /api/v1/Login`; la respuesta trae el `accessToken` (header `X-Auth-Token` de ahí en más) **y los contratos de la cuenta** — no hace falta conocer `cliente` ni `contrato`, los devuelve la API. Cotización: `POST /api/v1/Pyme/rates` con `{postal_code_origin, postal_code_destination, products[{quantity, price, dimensions{width,height,depth,grams}}]}`. Exige los 4 datos de peso/dimensiones de cada producto (de ahí la V14); si falta alguno no se cotiza. La modalidad "sucursal" viene repetida una vez por punto de retiro del CP → hay que quedarse con el mínimo por modalidad.
- **El costo de envío también se congela.** Mismo criterio que los precios: el checkout manda solo CP + modalidad, `PedidoService` **recotiza server-side** y guarda el importe. Si Andreani no responde en ese momento, el pedido igual se crea con `costo_envio_ars` en null ("a cotizar") — la cotización nunca bloquea una venta.
- **La home (`/`) es la TIENDA.** **El sorteo salió de la web el 2026-10-02** (pedido del usuario): no hay páginas, banner, pasos ni textos; `/sorteo`, `/inicio` y `/bases-y-condiciones` redirigen a `/` porque esos links siguen circulando. El registro ya no pide DNI, Instagram ni aceptar bases (las columnas siguen en la base con los datos de antes). **El sorteo igual se hace el 31/10/2026** entre los inscriptos: los códigos y chances (`usuarios.codigo_sorteo`, `chances_sorteo`) y Admin → Usuarios (validar Instagram/WhatsApp, exportar) quedan hasta entonces — después se pueden borrar. Tecnito tiene una regla para contestar solo si le preguntan.
- **Armá tu PC (`/arma-tu-pc`, 2026-09-22).** `GET /api/arma-tu-pc/componentes` (público) lista **solo Elit e Invid** — los únicos con ficha técnica completa — y `ComponentePcExtractor` lee de nombre + ficha socket, DDR, formato, ranuras de RAM, watts, video integrado y cooler incluido; no hay columnas, se calcula por request. Tres cosas aprendidas midiendo contra el catálogo real (`ComponentePcExtractorCatalogoRealTest`):
  - **El tipo sale del encabezado del nombre antes que de la categoría**: "Coolers > Fans" tiene fuentes y gabinetes de Cooler Master, y "Memoria DDR4" tenía 34 tarjetas SD.
  - **Sin socket escrito, se deduce** por chipset (B650 → AM5) o por generación del CPU (i5-12400 → LGA1700). Micro-ATX **no** fija la cantidad de ranuras (sale con 2 y con 4): queda null y el front avisa.
  - **Solo se bloquea lo cierto** (socket, DDR, kit que no entra en las ranuras); formato de gabinete, potencia de fuente y datos faltantes son aviso. Un null nunca oculta un producto.
  La placa de video es obligatoria solo si el CPU no tiene video. El cooler es obligatorio **salvo que se sepa que el CPU lo trae** (un equipo sin refrigeración no arranca): el dato sale de la ficha de Elit ("CPU cooler incluido: Sí/No"), del nombre de Invid ("CON COOLER" / "C/cooler") o del código de caja de Intel (BX… sin "K"). "Agregar todo al carrito" usa el carrito normal, así que el precio lo recalcula el backend como siempre.
  El envío del armado se cotiza con el mismo `POST /api/envio/cotizar` del checkout (todas las piezas juntas). Un armado se comparte por link: `?armado=cpu:<varianteId>,ram:<varianteId>x2,…`; los códigos cortos están en `CODIGO_LINK` de `ArmaTuPcPage` y **renombrarlos rompe los links ya enviados**. El 2º disco es un paso aparte (`clave` ALMACENAMIENTO_2, `tipo` ALMACENAMIENTO).
  **Cuellos de botella (2026-09-23):** `gama` 1–5 para procesador (línea + generación) y placa de video (tabla por chip). Diferencia de 2 gamas o más = sugerencia, **nunca bloqueo**: es una guía para juegos, y para edición o render puede convenir justamente un procesador fuerte con una placa modesta.
- **Límite de intentos (`LimitadorIntentos`, 2026-09-30).** Ventana deslizante en memoria (una sola instancia en Railway; un reinicio lo pone en cero). Login: 5 fallos por email bloquean 15 min (se chequea ANTES de comparar la contraseña, un acierto reinicia) + 20 intentos/10 min por IP. Registro 5/h por IP, recuperar contraseña 3/h por email (pasado el tope no manda el mail pero responde igual, para no revelar cuentas) y 5/h por IP, botón de arrepentimiento 3/h por IP y por email. **Lo que protege una cuenta es el límite por email:** la IP sale de X-Forwarded-For y se puede falsear.

## Límites conocidos (escalabilidad)
Medido el 2026-07-31 con **1.545 productos activos**. Nada de esto está roto hoy, pero son los techos que hay que mirar cuando el catálogo crezca.
- **N+1 del catálogo — resuelto (2026-08-02).** `CatalogoService` y `ProductoAdminService` hacían una query de variantes (y el catálogo, además, de imágenes) **por producto**: con 1.545 productos, ~3.100 queries por request y `GET /api/productos` en 9-14 s. Se cambió a `findByProductoIdInAndActivo` / `findByProductoIdInAndActivoOrderByOrden` (una sola consulta con `IN` para todo el catálogo) + agrupar por producto en memoria (`Collectors.groupingBy`). Bajó a un puñado de queries totales, sin importar cuántos productos haya. Si en algún momento vuelve a sentirse lento, revisar que ningún código nuevo haya vuelto a meter una consulta dentro del loop de productos.
- **El catálogo público se pagina y filtra en el servidor (2026-09-25).** `GET /api/productos/buscar?cat=&marca=&q=&min=&max=&orden=&page=&size=` devuelve 24 productos (tope 96) más las facetas del catálogo **completo** (marcas, categorías con productos, rango de precios), y la home usa `GET /api/productos/portada` (total, cantidades por categoría raíz, 8 destacados y un hero por categoría). Primera página: ~19 KB contra ~550 KB de la lista entera. **El filtrado va en memoria, no en SQL, a propósito:** el filtro y el orden por precio usan el precio de venta, y llevarlo a una consulta duplicaría la fórmula de `PrecioService`. Cada request arma el catálogo entero (~50 ms local con 766 productos); si alguna vez pesa, cachear `listarCatalogo()` unos segundos, sabiendo que un cambio de margen tardaría eso en verse. `GET /api/productos` (todo) queda por compatibilidad y ya no lo usa el front. `BusquedaCatalogo` replica la semántica del filtro que antes hacía el navegador (el "sin precio" pasa un mínimo pero no un máximo, y va siempre al final).
- **Filtros por características del catálogo (2026-09-29: iPhone, Celulares, Monitores y Placas de video).** Monitores: pulgadas (también la cifra suelta de LG/Raptor, "MONITOR LG 27 ULTRAGEAR"), Hz, resolución y pantalla (sin "curvo" = Plana, acordado). Placas: serie → chip → memoria (ASUS escribe "O8GB"). Memorias RAM: tipo (DDR3L = DDR3), formato PC/SODIMM, capacidad TOTAL ("2x16GB" = 32GB), módulos, MHz, RGB; "16Gbit" es la densidad del chip, no la capacidad. Notebooks: procesador por familia, RAM, almacenamiento, pantalla en rangos (13", 14", 15.6", 16", 17" o más) y placa ("Integrada" si no menciona una dedicada: siempre la nombran). La pantalla sin cifra explícita sale de reglas de fabricante — línea ("ThinkBook 16", "V15", "Katana 15"), código (Lenovo "15ARP10E", HP "15-FD…", ASUS "X1504", "Strix G16") o HP 240/250 —, sin Jev: 89% medido; líneas que salen en varios tamaños ("IdeaPad Slim 3", "Yoga 7") quedan sin dato. Los grupos valen para la categoría entera y sus hojas; "Apple > Monitores" no entra. `FiltrosCategoria` lee del nombre y la ficha, al armar el catálogo (no se guarda nada): iPhone → modelo (generación), versión, capacidad, color; Celulares → capacidad, RAM (también el formato "8+256" de Samsung/Xiaomi, que la identidad no lee), red, color. El grupo sale de la ruta de la categoría ("Apple > iPhone", "Celulares"), no del id. `BusquedaCatalogo` filtra con OR dentro de un atributo y AND entre atributos, y cuenta cada opción con los OTROS filtros aplicados. Reglas acordadas con el usuario: sin el dato, el producto no aparece al filtrar por ese atributo pero sí sin filtro; el color desconocido o múltiple es una opción más, **"Color a consultar"**; el color se muestra como lo nombra el fabricante (lo que sigue a la capacidad en el nombre) y "Ice Blue"/"Iceblue" se agrupan. Medir antes de sumar categorías: `mvn test -Dtest=FiltrosCategoriaCatalogoRealTest -Dcatalogo=/ruta.json`.
- **El buscador del admin filtra en el cliente** (`ProductosPage`), sobre el listado completo que ya viene cargado. A este volumen es instantáneo; si el catálogo crece un orden de magnitud hay que pasarlo a server-side junto con la paginación.
- **Un read timeout NO protege contra un servidor que manda keep-alives.** `setReadTimeout` mide el tiempo **entre bytes**, no el total de la llamada. DeepSeek, mientras espera para empezar la inferencia, no devuelve error: mantiene la conexión viva mandando líneas vacías, y recién la cierra a los 10 minutos. Cada línea reinicia el timeout, así que el de 180 s **nunca podía saltar**. El 2026-09-14 eso dejó una request colgada más de 7 minutos, sin error y sin log: el navegador se rendía y el admin veía una pantalla muda. Por eso `GenerarListadoService.generar()` corre la llamada en un hilo aparte con un **tope duro de 150 s** (`Future.get`), por debajo de los 240 s del navegador — es lo único que corta esto. `cancel(true)` no rescata al hilo trabado: se lo abandona a propósito, es preferible perder un hilo del pool a perder la pantalla. **Toda llamada saliente nueva que pueda colgar una request de usuario necesita un tope total**, no alcanza con timeouts de socket.
- **DeepSeek desde Railway encola; desde una máquina de escritorio no.** Medido el 2026-09-14 con la misma clave y el **payload idéntico** (prompt de 2.526 caracteres, `max_tokens` 8000): desde la Mac responde **200 en 1,27 s**, desde Railway se cuelga hasta que lo abandonamos. La cola es por IP y las de datacenter quedan atrás. No hay nada que arreglar del lado del código: si el generador tiene que andar, hay que usar otro proveedor. Detalle aparte: DeepSeek ya no sirve `deepseek-chat` con ese modelo, responde `deepseek-flash`.
- **Un error de IA nunca debe llegar mudo.** Las tres ramas de `GenerarListadoService.generar()` atrapan `HttpStatusCodeException` y traducen el código a un mensaje accionable, y `CargaJsonController` **loguea antes de responder** (`warn` para el 503, `error` con stack para el 502). Vino de un caso real: Anthropic devolvió 400 por tope de uso, el admin leyó "Revisá la conexión o la configuración de IA" y los logs de Railway quedaron vacíos — la rama de Anthropic era la única sin `try/catch` y el `catch (Exception)` del controller no escribía nada. **Al agregar un proveedor nuevo, copiar las dos mitades del patrón.** Detalle del mapeo de Anthropic: el saldo agotado y el tope de gasto llegan como **400**, no como 402, así que se detectan por el texto del `error.message`, que además se repite al admin tal cual (dice más que cualquier texto propio).
- **Apple va SIEMPRE a su propio árbol (V38).** `ClasificadorPorNombre#resolverApple` corre antes que todas las demás reglas y manda la marca Apple a `Apple > {iPhone, iPad, Mac, MacBook, Watch, AirPods, Monitores, Accesorios}`. Sin eso, el árbol genérico se los repartía: iPhone en "Celulares", MacBook en "Notebooks > Consumo", **iMac y Mac mini también** (y no son notebooks), Magic Mouse en "Periféricos > Mouse" — 107 de 263 al 2026-09-15. Tres detalles que se aprendieron probando:
  - **Los accesorios van primero**, porque casi todos nombran al aparato que acompañan: `Magic Keyboard iPad Air` es un accesorio, no un iPad. El patrón incluye `keyboard|folio|mouse|pencil|funda|case|correa|cable|…`, no solo "magic".
  - **Solo la marca Apple.** Una funda de Spigen para iPhone no entra al árbol.
  - **Nintendo Switch con la misma prioridad que Apple (2026-09-26):** "switch" también es un equipo de red; una pista o una categoría vieja (un producto que se ACTUALIZA no se reclasifica solo) las dejaba en "Switches No Administrables". El botón "Clasificar categorías faltantes" recorre también los dados de baja, así un alta futura no hereda la categoría equivocada.
  - **Tarjetas de memoria con la misma prioridad (2026-09-26):** Elit las informa como "Memoria DDR4" y esa pista las mandaba a Memorias RAM (34). `CategoriaClasificadorService#esTarjetaDeMemoria` decide por cómo EMPIEZA el nombre ("Tarjeta de Memoria…", "MicroSD…"), así no atrapa parlantes "con MicroSD" ni adaptadores "USB a SD"; el botón Clasificar también las reubica.
  - **La regla de Apple le gana también a la categoría sugerida por la carga (2026-09-26).** `CategoriaClasificadorService#clasificar` la corre ANTES que la pista: n8n manda "Celulares" para iPhone y iPad +Cell y esa pista ganaba (36 Apple fuera de su árbol). El botón "Clasificar categorías faltantes" de Admin → Productos también reubica los Apple que estén fuera del árbol Apple.
  - **Un Apple que no matchea cae en `Apple > Accesorios`, nunca en null** — es la excepción deliberada a la regla de "ante la duda, null" de este clasificador, porque sin categoría no se resuelve el peso y `EnvioService` corta la cotización del **carrito entero**.
- **El paso de IA del clasificador puede ser Jev (TypeSafe), 2026-09-28.** Con `TYPESAFE_API_KEY`, `CategoriaClasificadorService` le pide a Jev que elija la hoja de la lista cerrada (sin "Destacados") y **no llama a Claude** en ese paso, ni siquiera cuando Jev duda: por debajo de `TYPESAFE_CONFIANZA_MINIMA` (0.7) queda null, que es el "ante la duda, null" de siempre. Jev solo acepta texto y no navega: **no sirve para buscar imágenes**. Medido contra la base local (`ClasificacionIaCatalogoRealTest`, gasta API real): misma precisión que Claude Haiku (sus dos "errores" fueron discos WD Red/Purple a NAS, defendible), ~350 ms contra ~800 ms. Los desacuerdos con la categoría guardada fueron casi todos etiquetas mal cargadas en la base (fuentes Cooler Master en "Coolers > Fans", un Galaxy en Sillas).
- **Clasificación de categorías sin IA (`ClasificadorPorNombre`).** El vocabulario de categorías de Elit no calza con el árbol, y como el último recurso del clasificador era Claude (sin crédito), el 60% del catálogo quedaba con `categoria_id` en null — y sin categoría no se resuelve el peso, así que esos productos **no cotizan envío** (peor: `EnvioService` corta la cotización del **carrito entero** si un solo ítem no resuelve medidas). Se resuelve por reglas sobre el nombre, antes de la IA. **Clave: mira solo las primeras 4 palabras del modelo**, donde el mayorista pone el tipo de producto; el resto son especificaciones que mienten ("Procesador ... con Cooler" no es un cooler). Medido: leer el nombre entero da 31% de errores, leer el encabezado lo baja a 7%. La subcategoría sí usa el texto completo (chipset, Hz, si un switch es administrable). Ante la duda devuelve null a propósito: mal categorizado hereda un peso equivocado y cotiza mal sin que nadie se entere. Hay un test contra un volcado del catálogo real: `mvn test -Dtest=ClasificadorPorNombreCatalogoRealTest -Dcatalogo=/ruta/catalogo.json`.
